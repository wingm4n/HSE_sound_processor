# sound_processor

Небольшая консольная утилита на **C++17**: читает моно 16-bit PCM `.wav` файл, пропускает его через настраиваемую цепочку аудиоэффектов и записывает результат на диск. Также умеет синтезировать звук с нуля (синусоида и амплитудно-модулированный тон).

Проект намеренно не имеет внешних зависимостей (только STL и POSIX `getopt_long`). Разбор и запись WAV, парсинг аргументов и DSP-код написаны вручную. Главная цель проекта — отработать чистый OOP-дизайн, безопасную работу с ресурсами и обработку ошибок в современном C++.

```bash
# Сгенерировать 1 секунду тона 440 Гц, затем применить цепочку из 5 эффектов
./sound_processor -o tone.wav -f generator sin 440 1000
./sound_processor -i tone.wav -o out.wav \
    -f ampl 0.5 -f lowpass 5 -f timestretch 2 -f silence ms 100 200 -f normalize 0.9
```

## Возможности

- **Собственная реализация WAV I/O.** Заголовки RIFF/`fmt `/`data` отображаются на структуры с `__attribute__((packed))` и читаются или записываются одним вызовом.
- **Конвейер фильтров.** Любое количество опций `-f` выстраивается в цепочку и выполняется в заданном порядке. Один и тот же фильтр можно использовать несколько раз.
- **6 фильтров:** усиление, нормализация, вставка тишины, изменение темпа (time-stretch), low-pass и генераторы сигналов (синус и AM).
- **Расширяемость.** Для нового фильтра нужен один класс, одна фабричная функция и одна строка регистрации. Существующие фильтры и парсер менять не требуется.
- **Строгая обработка ошибок.** Неверные аргументы, неизвестные фильтры, повреждённые или отсутствующие файлы приводят к типизированным исключениям. Они обрабатываются в одном месте (`main`) и превращаются в ненулевой код возврата.
- **Арифметика с насыщением.** Каждое обратное преобразование в `int16_t` проходит через clamp, поэтому переполнение не превращается в громкие искажения.
- **Unit-тесты** на Catch2, сборка с `-Wall -Wextra` и AddressSanitizer/LeakSanitizer.

## Сборка и запуск

**Требования:** компилятор с поддержкой C++17 (GCC/Clang) на Linux или macOS и CMake ≥ 3.14. Код использует POSIX `getopt_long` и расширения GNU (`M_PI`, packed-структуры), поэтому MSVC не поддерживается. Catch2 v3 для тестов скачивается автоматически.

```bash
git clone <your-repo-url> sound_processor
cd sound_processor

cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j

./build/sound_processor --help
```

Опции CMake:

| Опция | По умолчанию | Значение |
|---|---|---|
| `ENABLE_SANITIZERS` | `ON` | Сборка с `-fsanitize=address,leak` |
| `BUILD_TESTING` | `ON` | Сборка тестов на Catch2 (скачивается Catch2 v3.5.2) |

## Использование

```
sound_processor [-i <input.wav>] [-o <output.wav>] [-f <filter> [params...]]...
sound_processor -h | --help
```

| Опция | Длинная форма | Описание |
|---|---|---|
| `-i` | `--input` | Входной WAV-файл. Если не указан, обработка начинается с пустой волны. Удобно вместе с `generator`. |
| `-o` | `--output` | Выходной WAV-файл. Если не указан, выводится предупреждение и ничего не сохраняется. |
| `-f` | `--filter` | Имя фильтра и его параметры. Повторяйте опцию, чтобы построить цепочку. |
| `-h` | `--help` | Вывести справку. |

Всё, что идёт после `-f <name>` и не похоже на опцию, считается параметром этого фильтра. Отрицательные числа вроде `-0.5` по-прежнему разбираются как параметры.

**Коды возврата:** `0` — успех (в том числе для `--help`), `1` — обработанный `std::exception` (плохой файл, неверные аргументы фильтра и т. п.), `2` — неизвестное исключение, `-1` (в shell: 255) — фильтр сообщил об ошибке.

**Примеры**

```bash
# Сделать тише и сгладить высокие частоты
./sound_processor -i in.wav -o out.wav -f ampl 0.7 -f lowpass 9

# Воспроизвести вдвое медленнее (в два раза длиннее, ниже по тону), затем нормализовать до 90% от full scale
./sound_processor -i in.wav -o slow.wav -f timestretch 2 -f normalize 0.9

# Вставить 500 мс тишины на второй секунде
./sound_processor -i in.wav -o gap.wav -f silence sec 2 2.5

# Синтезировать 2 секунды тона 440 Гц с тремоло 5 Гц (амплитуда 80%, глубина 50%)
./sound_processor -o tremolo.wav -f generator am 0.8 440 5 0.5 2000
```

## Справочник по фильтрам

| Фильтр | Параметры | Описание |
|---|---|---|
| `ampl` | `factor` ≥ 0 | Умножает каждый сэмпл на `factor` с насыщением по границам `int16`. |
| `normalize` | `[peak]` в [0, 1], по умолчанию `1` | Масштабирует сигнал так, чтобы самый громкий сэмпл достиг `peak × full scale`. Тихий сигнал (одни нули) не изменяется. |
| `silence` | `unit` (`sec`\|`ms`), `start`, `end` (`end ≥ start`) | **Вставляет** блок нулей в позицию `start`, охватывающий `[start, end]`. Хвост сдвигается вправо, поэтому трек становится длиннее. Если `start` находится за концом аудио, трек сначала дополняется тишиной до этой точки. |
| `timestretch` | `factor` > 0 | Ресемплирует сигнал до `round(N × factor)` сэмплов с помощью **линейной интерполяции**. Поле частоты дискретизации не меняется, поэтому длительность и высота тона меняются вместе. |
| `lowpass` | `window` (нечётное целое ≥ 1) | Фильтр скользящего среднего с заданным размером окна. Края сигнала обрабатываются ограничением индекса (первый и последний сэмплы повторяются). |
| `generator sin` | `freq` (Гц), `duration` (мс) | **Заменяет** волну синусоидой полной амплитуды. |
| `generator am` | `amp` [0,1], `carrier` (Гц), `mod` (Гц), `depth` [0,1], `duration` (мс) | **Заменяет** волну амплитудно-модулированным тоном: `amp · (1 + depth·sin(2π·mod·t)) · sin(2π·carrier·t)`. |

Генераторы всегда создают моно-аудио с частотой 44.1 кГц.

## Архитектура

Программа разбита на небольшие слои с единственной ответственностью. Вся логика находится в статической библиотеке (`lib`), с которой линкуются и исполняемый файл, и тесты.

Поток данных можно описать так:

```
argv ──► ArgsParser ──► vector<FilterDescriptor> ──► CmdLineArgs2PipelineConverter ──► Pipeline
                                                       (реестр «имя → фабрика»)          │
input.wav ──► WaveReader ──► Waveform ───────────────────────────────────────────────────┤
                                                                                          ▼
                                                      output.wav ◄── WaveWriter ◄── Waveform
```

Основные классы:

- `IFilter` — интерфейс с методом `apply(Waveform*) -> bool`. Его реализуют `AmplFilter`, `NormalizeFilter`, `SilenceFilter`, `TimestretchFilter`, `LowpassFilter` и `AbstractGeneratorFilter` (от него наследуются `SinGenFilter` и `AmGenFilter`).
- `Pipeline` — владеет `vector<unique_ptr<IFilter>>`, методы `addFilter(...)` и `apply(Waveform*)`.
- `CmdLineArgs2PipelineConverter` — хранит `map<string, FilterProducer>`, методы `addFilterProducer(name, producer)` и `createPipeline(descriptors)`.

### Структура проекта

```
.
├── main.cpp                  # точка входа: единственное место, где ловятся исключения
├── include/
│   ├── application.h         # связывание: регистрация фильтров, цикл чтение → обработка → запись
│   ├── argsparser.h          # разбор командной строки
│   ├── descriptor.h          # FilterDescriptor: «имя фильтра + сырые строковые параметры»
│   ├── pipeline.h            # Pipeline + конвертер/реестр фабрик
│   ├── filters.h             # IFilter и все конкретные фильтры
│   ├── waveform.h            # аудио в памяти (структуры заголовков + vector<int16_t>)
│   ├── riffstruct.h          # packed-структуры заголовков RIFF / fmt / data
│   └── wavestream.h          # WaveReader / WaveWriter + типы исключений
├── src/                      # реализации
└── tests/test_sound_processor.cpp
```

### Поток данных

1. `ArgsParser` превращает `argv` в значения `-i`/`-o` и список `FilterDescriptor`. Дескриптор — это имя фильтра плюс его ещё не разобранные строковые параметры.
2. `CmdLineArgs2PipelineConverter` ищет каждое имя в реестре (`std::map<std::string, FilterProducer>`). Подходящая фабричная функция проверяет и преобразует параметры и возвращает конкретный фильтр. Результат — `Pipeline`.
3. `WaveReader` загружает входной файл в `Waveform`.
4. `Pipeline::apply` последовательно применяет фильтры к одному и тому же `Waveform`. Выполнение останавливается на первом фильтре, вернувшем `false`.
5. `WaveWriter` пересчитывает размеры в заголовках по фактическим данным и записывает файл.

## Детали реализации

Несколько проектных решений, которые могут быть интересны:

- **Strategy + Factory/Registry.** `IFilter` — абстрактная стратегия. `Application::configure()` регистрирует по одной фабричной функции на каждое имя фильтра. Чтобы добавить фильтр (например, `reverse`), нужно написать класс, функцию `reverseFilterCreator` и один вызов `addFilterProducer("reverse", ...)`. Код парсера и конвейера не меняется (Open/Closed Principle).
- **Владение и RAII.** `Pipeline` владеет фильтрами через `std::unique_ptr<IFilter>`, поэтому он явно **move-only** (операции копирования `= delete`, в соответствии с rule of five). У `IFilter` виртуальный деструктор.
- **Разделение парсинга и валидации.** Фабричные функции проверяют только *форму* входных данных (число аргументов и преобразование в число). Конструктор и `apply` каждого фильтра проверяют *семантический* диапазон (например, `peak` в `normalize` должен быть в [0, 1]). Ошибки сообщаются через `std::logic_error` или `FilterBadArgs`.
- **Типизированные исключения для I/O.** `WavestreamWrongFile`, `WavestreamBadContent`, `WavestreamReadError` и `WavestreamWriteError` наследуются от `std::runtime_error`. Потоки работают с включёнными исключениями `failbit | badbit`, а низкоуровневый `ios_base::failure` преобразуется в собственные типы исключений проекта.
- **Работа с бинарным форматом.** `RiffHeader`, `FmtHeader` и `FmtChunk` — `packed`-структуры, отображающиеся 1:1 на раскладку на диске. Размеры чанков при записи вычисляются по реальному числу сэмплов, поэтому любой фильтр, меняющий длину (`silence`, `timestretch`, `generator`), всё равно даёт согласованный файл.
- **Внимание к алгоритмам.** `lowpass` — скользящее среднее за **O(N)** со скользящей суммой: окно не пересуммируется для каждого сэмпла. Сумма хранится в `long long`, чтобы избежать переполнения. `timestretch` использует линейную интерполяцию между соседними сэмплами.
- **Численная безопасность.** Единственная вспомогательная функция `doubleToInt16` ограничивает значение диапазоном `[-32768, 32767]` и отображает `NaN` в `0`. Её используют все фильтры.
- **Sanitizers по умолчанию.** Сборка идёт с `-Wall -Wextra`, AddressSanitizer и LeakSanitizer. Они рано выявляют ошибки работы с памятью (для release-сборки их можно отключить через `-DENABLE_SANITIZERS=OFF`).

## Тестирование

```bash
cmake --build build --target test_sound_processor
./build/test_sound_processor
```

Реализовано 11 тест-кейсов Catch2 (45 assertions). Они покрывают:

- разбор аргументов, включая несколько опций `-f` и параметры из нескольких значений;
- вычисление размеров `Waveform`;
- числовое поведение `ampl` (включая clipping), `normalize`, `silence`, `timestretch`, `lowpass` и `generator sin`;
- запуск нескольких фильтров в `Pipeline`;
- пути ошибок в конвертере (неизвестный фильтр, нечисловой параметр, отсутствующий параметр) и в reader (несуществующий файл).

## Известные ограничения и планы

Область проекта намеренно узкая: **моно, 16-bit PCM, 44.1 кГц** (частота дискретизации при чтении не проверяется). Ниже места, которые, как мне известно, можно улучшить, примерно в порядке важности:

- **WAV reader минималистичен.** Он ожидает каноническую раскладку (`RIFF` → 16-байтовый `fmt ` → `data`) и не пропускает дополнительные чанки вроде `LIST`. Поля `fmt ` не проверяются, поэтому стерео или не 16-bit файл будет загружен и пересохранён, но фильтры будут воспринимать чередующиеся сэмплы как один канал. Кроме того, reader доверяет размеру чанка `data` из заголовка, поэтому повреждённое поле размера может вызвать попытку выделить огромный объём памяти. Решение: разбирать чанки в цикле, проверять формат (PCM, число каналов, разрядность) и сверять заявленный размер с реальным размером файла.
- **`ArgsParser` использует глобальное состояние `getopt`** (`optind`) и хранит сырые указатели `char*` на `argv`. Он не re-entrant, и тестам приходится вручную сбрасывать `optind`. Небольшой самодостаточный парсер устранил бы обе проблемы.
- **Фабричные функции возвращают сырые указатели** (`IFilter*`) через указатель на функцию в стиле C. Возврат `std::unique_ptr<IFilter>` и использование `std::function` сделали бы владение явным и позволили бы использовать лямбды.
- **Конец интервала в `silence` включается**, поэтому блок, охватывающий `[start, end]`, содержит на один сэмпл больше, чем `(end − start) × rate`. Кроме того, `Waveform::getDataSizeSec()` пока работает неверно (делит на разрядность, а не на byte rate), но ни один фильтр его не использует.
- **Возможные доработки:** поддержка стерео, echo/reverb, fade in/out, ресемплинг, полноценный FIR/IIR low-pass, потоковая обработка больших файлов и интеграционный тест, выполняющий round-trip сгенерированного WAV.
- **CI.** Естественным следующим шагом стал бы workflow в GitHub Actions, который собирает проект GCC и Clang и запускает тесты.
